# FRR #14818 — link-local nexthops unresolved on the passive side

**Investigated with AI-TAC / fr trace against a live bgpd. Result: does NOT
reproduce on FRR 10.8.0-dev — the nexthop resolves correctly.**

## The ticket
[#14818](https://github.com/FRRouting/frr/issues/14818): on the passive side of
an unnumbered IPv6 link-local eBGP session with `capability extended-nexthop`,
IPv4 routes with IPv6 nexthops stay unresolved — `bgp_update(0.0.0.0): NH
unresolved`, `Allocated bnc fe80::.../128 ... peer 0x0`. Introduced by commit
`0c3a70c64430448c43fe12bf0ac044488352697c`.

## Reproduction built (the exact triggering conditions)
Two network namespaces, one veth pair, an **unnumbered IPv6 link-local eBGP**
session, IPv4 advertised over an IPv6 nexthop, ns2 the **passive** side:

    ns1 (AS 65001, active)         ns2 (AS 65002, passive)
      neighbor veth1 interface       neighbor veth2 interface remote-as external
        remote-as external           neighbor veth2 capability extended-nexthop
      neighbor veth1 capability      neighbor veth2 passive
        extended-nexthop           + ipv6 nd RA on veth2 (unnumbered discovery)
      network 172.16.1.0/24

## Observed on the live passive bgpd (ns2)

    # show bgp ipv4 unicast
      Network         Next Hop   ...
    *> 172.16.1.1/32  veth2      ...        <- valid (*), best (>)

    # show bgp nexthop
    fe80::f5ff:fe9e:5563  valid [IGP metric 0], #paths 1, peer veth2
                          ^^^^^  <- RESOLVED, not "NH unresolved"

No `NH unresolved`, no `peer 0x0` in the logs. The link-local nexthop
resolves, the route is installed best, and it **stays valid across repeated
route flaps** (verified while attached).

## Runtime tracing
`fr trace attach` on the live passive bgpd (pid from /var/run/frr/ns2), probing
the nexthop path (`bgp_find_or_add_nexthop`, a real exported symbol at
0x1d2318). The daemon kept serving throughout; `show bgp nexthop` under the
probe consistently reported the bnc **valid**. Note:
`bgp_find_or_add_nexthop` is not re-invoked on a simple re-advertisement of an
already-cached nexthop, so flaps of the same prefix do not re-hit it — the
resolution state is read from cache and remains valid.

## Conclusion
On **FRR 10.8.0-dev**, #14818 does not reproduce: the passive-side link-local
nexthop resolves correctly. The bug introduced by `0c3a70c6` appears fixed in
this version. For a maintainer triaging the ticket, this is the useful signal —
"cannot reproduce on current dev; likely resolved since the introducing
commit" — established by building the exact conditions and observing the live
daemon, not by reading code.

_Honest scope: this confirms non-reproduction on one version + topology. It
does not bisect which commit fixed it, and does not test the pure-IPv6-route
variant the reporter flagged as "likely also affected."_
